# Agent instructions

Provenance: unreviewed. An agent wrote this, and the user has not marked which parts are the user's decisions. Treat every claim as an agent's, see [decisions/0019](docs/decisions/0019-provenance-of-documents.md).

- Provenance: never write a reason, decision or rule as the user's unless the user gave it. Agent reasoning goes under an `Agent notes` heading, or in a file marked `agent`. A record marked `agent` or `unreviewed` is a default: follow it, challenge it when evidence says otherwise, and tell the user. Every Markdown file under [`docs/`](docs/) and [`design/`](design/), [`GLOSSARY.md`](GLOSSARY.md) and this file states its provenance, in front matter or a `Provenance:` line, and decision records only in front matter; meeting notes carry neither, and [`docs/check.py`](docs/check.py) enforces all of it ([decisions/0019](docs/decisions/0019-provenance-of-documents.md)). Decided by the user on 2026-09-25.
- Front matter holds `created`, `provenance`, `description` and, when replaced, `superseded_by` ([decisions/0019](docs/decisions/0019-provenance-of-documents.md)). Never add a `related` field: the links in the text are the only record of what relates to what. Decided by the user on 2026-09-25.
- Product work: read [the system plan](docs/projektplan.md), [requirements](docs/requirements.md), and [glossary](GLOSSARY.md). Update the glossary in the same commit when a term changes meaning or is added.
- Task tracking: work is on the [Kanban project](https://github.com/users/AlexanderReaper7/projects/1), explained for the team in [onboarding](docs/onboarding.md), one parent issue per requirement with work items as sub-issues, run as Kanban in weeks with sizes, work-in-progress limits and set meetings, and a daily check from [kanban-weeks](https://github.com/AlexanderReaper7/kanban-weeks), configured in [`kanban.toml`](kanban.toml), reports what breaks them ([decisions/0018](docs/decisions/0018-kanban-with-weekly-syncs.md)). Decided by the user on 2026-09-25.
- Branches and pull requests: every change, the owner's agents' included, reaches main through a pull request that only the user merges, and its description says `Closes #N` or it carries the label `no-issue` ([decisions/0020](docs/decisions/0020-pull-requests-and-merging.md)). Start a worktree with `gh issue develop <N> --name <N>-<slug> --worktree <path>`. The team's guide is [branches-and-pull-requests](docs/branches-and-pull-requests.md). Decided by the user on 2026-09-27.
- Requirement ids are `R001` upwards, never reused, and a new requirement takes the next number. An id may be followed directly by its issue, as in `R005 #8`, and [`docs/check.py`](docs/check.py) fails if two documents give one id different issues. The rules are in [requirements](docs/requirements.md). Decided by the user on 2026-09-25.
- Meeting documents are named by date and a slug, per [the naming convention](docs/meetings/naming-convention.md), and [`docs/check.py`](docs/check.py) enforces it. Decided by the user on 2026-09-25.
- Questions for the customer go in the next meeting's document under [`docs/meetings/`](docs/meetings/), which records the answers. [open-questions](docs/open-questions.md) holds only questions that cannot be asked at the next meeting. Decided by the user on 2026-09-25.
- Technical choices: read the relevant record in [decisions](docs/decisions/). New evidence may overturn a decision, but the record and plan must change with it, git provides additional history.
- Customer source: keep [`docs/projektplan-original.md`](docs/projektplan-original.md) and [`docs/projektplan-original.en.md`](docs/projektplan-original.en.md) frozen, old requirement ids `P1` to `U4` included. They map to `R001` to `R025` by row order.
- Documentation changes: run the check defined in [.github/workflows/docs.yml](.github/workflows/docs.yml).
- Links: everything that can be a link is one. [`docs/check.py`](docs/check.py) fails on a bare URL and on an unlinked path to a tracked file or directory, written in full or as the end of exactly one file's path, and `python3 docs/check.py --fix-links` rewrites them. A decision number, a commit hash and anything else it cannot tell apart from plain text are linked by hand. Requirement ids and issue numbers stay plain text, because links there clutter. Decided by the user on 2026-09-26.
- Code changes: build and test through docker, never a local JDK. Commands are in [README.md](README.md), and as VS Code tasks in [`.vscode/tasks.json`](.vscode/tasks.json), reasoning in [decisions/0011](docs/decisions/0011-maven-and-the-build-in-a-container.md). Run `verify`, not `test`: Checkstyle runs at `validate`, SpotBugs and PMD at `verify`, and all three fail the build ([decisions/0013](docs/decisions/0013-three-static-analysis-gates.md)).
- Java doc comments are `///` Markdown (JEP 467), never `/** */`. Checkstyle rejects `/** */`, but nothing checks what a `///` comment contains, so `@param` and `@return` on public methods are on the author. Why, and the measurement behind it, in [decisions/0013](docs/decisions/0013-three-static-analysis-gates.md).
- End-to-end tests: `sh e2e/run.sh` runs the Playwright suite against its own stack ([decisions/0017](docs/decisions/0017-playwright-e2e-in-docker.md)). A test marked `test.fail()` is a known bug listed in [open questions](docs/open-questions.md); fixing the bug means removing the mark in the same commit.
- New capability: it goes on an application service, and both adapters get it. A JTE controller in `se.teaterihuskvarna.web` calls the service method directly; a `@RestController` in `se.teaterihuskvarna.api` wraps the same method. `AdapterRulesTest` fails the build if `api` falls behind, and the reasoning is in [decisions/0014](docs/decisions/0014-one-service-layer-two-adapters.md).
- Adapters never touch a repository or an entity. Services return records built inside the transaction, because `open-in-view` is off ([decisions/0012](docs/decisions/0012-jpa-over-a-schema-flyway-owns.md)). Keep repositories package private so the compiler enforces this before the test does.
- Do not add a SpotBugs exclusion without writing, beside it in [`spotbugs-exclude.xml`](spotbugs-exclude.xml), what the detector protects against and why that cannot reach this code. Do not raise the PMD pin or the `var` ban without reading [decisions/0013](docs/decisions/0013-three-static-analysis-gates.md) first: both look redundant and are not.
