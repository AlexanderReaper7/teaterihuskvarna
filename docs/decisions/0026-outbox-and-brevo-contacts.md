# 0026: An outbox for mail and Brevo, and members as Brevo contacts

The Decision section is the user's. Everything under Agent notes is an agent's.

## Decision

- Mail goes through an outbox: a table the change's own transaction writes to, and a job that retries until the mail is sent. Decided by the user on 2026-09-28, after the GPT-6 Sol review found that a shift reminder was marked as sent before the mail went, so a failed send was never retried.
- Brevo keeps one list with every member who has an account, and each contact carries attributes the association builds its audiences on as segments in Brevo, so it can write and send campaigns in Brevo without going through the application first. The user asked "cant we just keep the lists continuosly updated? so we have one list per audience that also doesnt depend on doing something inside the admin page first", and then chose one list with attributes over one list per audience. Decided by the user on 2026-09-28, after the GPT-6 Sol review found that a new list per mailing ([0023](0023-brevo-list-per-mailing.md)) never gets cleaned up, and Brevo allows 300 created lists.
- The contacts are updated on every change to the register, not by a comparison on a timer. Decided by the user on 2026-09-28.
- The mailing page stays, and creates its draft for the whole list or for a segment instead of a new list. Decided by the user on 2026-09-28.
- Before a draft goes to a segment, the application checks in Brevo that every contact in it is on the members' list, and refuses the segment otherwise. The user asked for safeguards beyond a written instruction: "The administrators might not be very hood with computers, so id like safeguards that are more than just 'follow the guide'", and chose this check alone over also keeping non-members out of Brevo or offering only fixed audiences. Decided by the user on 2026-09-29.

## Agent notes

Written by an agent on 2026-09-28. Everything below is a default the user has not reviewed.

### The outbox

- [`Outbox`](../../src/main/java/se/teaterihuskvarna/outbox/Outbox.java) writes a row in the caller's transaction and tries it on a background thread after the commit. A failed attempt waits one minute, then twice as long after each further failure, six hours at most. A row is never given up, following the decision above: after 10 attempts, about eight and a half hours, it is logged as an error once and tried every six hours. A row is deleted when its work is done, so the table holds only what is pending, and a row that stays is work that never succeeded, such as an address the relay refuses for good. Until the GPT-6 Sol review on 2026-09-29 the row was deleted after 10 attempts, which lost work after an outage of that length. [`V12__outbox.sql`](../../src/main/resources/db/migration/V12__outbox.sql) has the table.
- Each kind of work, mail and Brevo contacts, has one thread of its own for the attempts after a commit. An attempt holds a database connection while it waits on the other system, so a burst ties up one connection per kind plus the retry job's, and a slow Brevo never delays a login mail.
- An attempt locks its row with `FOR UPDATE SKIP LOCKED`, so the attempt after the commit and the retry job never do one row twice at once, and neither would two instances of the application.
- Work must be safe to repeat, because an attempt can succeed at the other end and still fail here, such as on a timeout. A mail sent twice in that case is the accepted cost.
- A login mail's link sits in the table in plain text until it is sent, normally within a second. Everywhere else only a token's hash is stored ([0015](0015-login-links-on-spring-security.md)). Someone who can read the table can read the other tables too, and the link expires on its own, so the agent judged the difference small.
- [`Mailer`](../../src/main/java/se/teaterihuskvarna/login/Mailer.java) keeps its rule that a response must not reveal whether an address is known: the mails that depend on an address are queued from `Background`, off the request thread, so the outbox row costs the request nothing.

### The Brevo contacts

- A contact is keyed by `ext_id`, the member's id, so a changed address moves the same contact and keeps its unsubscribe. The attributes are `NAMN`, `PAID_YEAR` (text holding the latest year the member's fee is paid, by themselves or their household), `LAST_SHIFT` (the day the latest shift they were booked on started) and `OFFERS` (the offers they are registered for, as `;12;15;`). The application creates the attributes on its first call. Everything is in [`HttpBrevo`](../../src/main/java/se/teaterihuskvarna/mailing/HttpBrevo.java).
- The audiences [0023](0023-brevo-list-per-mailing.md) named are segments the association saves in Brevo: every member is the list itself, paid this year is `PAID_YEAR` equal to the year, not paid is the opposite, volunteers are `LAST_SHIFT` within the last 12 months, and an offer's registrants are `OFFERS` containing `;<id>;`. The offer's page in the application shows that value. Brevo's API has no call that creates a segment, so they are made by hand, once, and the application offers every segment in the account. A segment must be built on the members' list, or a mailing to it reaches other contacts too, such as an administrator's address on the test list. [`MailingService`](../../src/main/java/se/teaterihuskvarna/mailing/MailingService.java) reads every contact in the segment before preparing a draft, a thousand a page, and refuses it if any is off the list; the preview shows how many members a mailing reaches and says why a segment cannot be used. The check is at preparing: the segment can change in Brevo before the administrator presses send there, and a campaign made directly in Brevo is not checked at all.
- The member, fee, offer and shift services publish `MemberChanged` in their transactions, and [`BrevoContactChanges`](../../src/main/java/se/teaterihuskvarna/mailing/BrevoContactChanges.java) writes an outbox row with the member's id. [`BrevoContacts`](../../src/main/java/se/teaterihuskvarna/mailing/BrevoContacts.java) reads the member as they are when the row is done, so a retry never sends an old state. A member who is gone, or has no account, has their contact deleted, so a deleted member's address leaves Brevo too.
- Brevo resubscribes a blocklisted contact whose address changes ([update-contact](https://developers.brevo.com/reference/update-contact)). So the contact is read before each update, the address is sent only when it has changed, and then a contact that is blocklisted gets `emailBlacklisted: true` sent back with it. An unsubscribe that lands between that read and an address change is lost, a window of milliseconds on a change only an administrator makes; closing it would need Brevo to report unsubscribes to the application. The application never unblocks a contact and never blocks one that was not.
- `PAID_YEAR` is text: Brevo ignores a value that does not match an attribute's type, so an empty string could not clear a number when a fee is undone. A numeric version existed only in unpushed commits on 2026-09-28, and no account has run it. Brevo cannot change an attribute's type once made, so an account that had created it as a number would need the attribute deleted by hand first. `LAST_SHIFT` stays a date, for segments such as the last 12 months, and is cleared with `null`, which the reference does not describe; it is cleared only when a started shift is deleted.
- Two outbox rows for one member could run at once and leave the older state in Brevo, so each row takes a PostgreSQL advisory lock on the member for its transaction before it reads the member.
- A household fee changes the contact of everyone in the household. `LAST_SHIFT` changes when a shift starts, with nothing written, so a job reports each shift once it has started, within five minutes, and `volunteer_shift.start_reported` records it.
- [`V13__brevo_contacts.sql`](../../src/main/resources/db/migration/V13__brevo_contacts.sql) queues every member with an account once, so the list starts complete, and drops the per-mailing list columns.
- A mailing no longer knows how many it reaches when it is prepared. The log shows Brevo's count of mails sent instead.
- The list is made once by hand in Brevo and named by `BREVO_LIST_ID`.
- Not verified against a real account: that `emailBlacklisted: true` sent with a new address keeps the contact blocklisted, that an empty string clears a text attribute and `null` a date, that Brevo answers 400 for an attribute that exists, and that a date attribute takes `yyyy-MM-dd`. They follow Brevo's API reference as read on 2026-09-28. [`HttpBrevoTest`](../../src/test/java/se/teaterihuskvarna/mailing/HttpBrevoTest.java) checks only the requests the application sends.
